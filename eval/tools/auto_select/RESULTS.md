# 자동 도구 선택 평가 결과 (v1 측정)

설계 문서 `docs/architecture/auto-tool-selection.md`(rev 3) §8, §11 질문에 대한 **측정값**이에요. 모든 숫자는 `results/*.json`에서 나왔고, 재현은 `README.md`의 `run_all.sh`, `report.py`, `report_extra.py` 순서예요. 측정 대상은 실제 서빙 중인 Qwen3-30B-A3B-4bit(:8080)이고, 요청은 항상 한 번에 하나씩만 보냈어요.

## 0. 먼저 읽을 한계

- 항목 130개(web_search 기대 68, none 기대 62). 홀드아웃은 34개(양성 17, 음성 17)뿐이라 **홀드아웃 1건 = 5.9%p**예요. 홀드아웃 단독으로 임계값 합격/불합격을 판정하기엔 작아요.
- 변형별로 **1회 실행**이에요(temperature 0.7, top_p 0.9). V0(web_on, /no_think)만 2회 했고 58.8% / 60.3%로 1.5%p 차이가 났어요. 변형 간 5%p 안쪽 차이는 노이즈로 봐야 해요(Wilson 95% 구간이 대략 ±10%p).
- 그룹 C(경계 50개)는 만들지 않았어요. 단일 라벨로 두고 어려운 항목에 `tricky`(38개)를 붙였어요. "경계 성향" 카테고리(latest_version, implied_recency)를 뺀 재현율을 같이 적어요(n=54).
- 그룹 D(캘린더)는 없어요. main에 캘린더 도구 정의가 아직 없어서 보류했어요.
- 도구 정의는 main `b72651d`의 `internal/tools/testdata/tooljson_v1.1.0.golden`(web_search, web_fetch)이에요.
- V4(같은 모델 한 단어 분류기)는 **측정만** 했고 게이트웨이에 통합해서 end-to-end로 돌려 본 건 아니에요.
- 서빙 프로브(§3)는 합성 한국어 채움 텍스트를 썼어요. 실제 웹 스니펫(영문 비중이 높으면 글자당 토큰이 적음)과 토큰 수가 다를 수 있어요.
- 설계 §8.5(주입 공격 확률 평가)와 echo-filter 오탐은 이번에 측정하지 않았어요.

## 2. 임계값 제안

1. **불필요 검색 ≤8%는 유지**하되 점추정만이 아니라 Wilson 상한도 함께 보고해요. 프롬프트 변형이 0–3%라서, 재현율을 올리려고 불필요 검색을 5% 안팎까지 쓰는 거래는 받아들일 만해요.
2. **재현율 ≥90%는 유지하되 판정 방식을 바꾸자고 제안해요.** (a) 프롬프트 동결 후 시드 3회 이상 반복, (b) 새 홀드아웃은 양성 60개 이상(지금 17개로는 1건=5.9%p), (c) "경계 성향" 카테고리는 별도 지표로 분리해 보고. 이 세트에서는 어떤 프롬프트 전용 변형도 90%에 닿지 못했으므로 **프롬프트만으로 90%를 약속하면 안 돼요.**
3. **90%를 반드시 지켜야 한다면 V4식 분류기 게이트(+ 게이트웨이 강제 검색)가 현재 유일한 후보**예요. 분류기는 0.39초(평균, 중앙값 0.36초, p95 0.48초)가 추가돼요. 단, 통합 전에는 end-to-end 재측정이 필요해요.
4. 지연 목표: thinking off(요청별 kwargs)에서 호출 결정까지 요청 전체 중앙값 1.30초, p95 1.85초(워밍된 캐시, 짧은 프롬프트 기준)로 §4.6의 p95 ≤3초 안이에요. thinking on은 중앙값 5.5초, p95 약 10–11초라서 `deciding` 신호 없이는 목표를 못 맞춰요. 시스템 프롬프트가 길어 prefill 캐시가 깨지면 §3.2 표처럼 훨씬 느려져요.

## 3. 서빙 프로브

### 3.1 mlx_lm `tool_choice` (질문 1)

`auto`/`none`/`required`/지정 `web_search` 네 가지를 양성 1개·음성 1개 프롬프트로 각 5회씩 시도했어요. **양성은 모든 모드에서 5/5 검색, 음성은 모든 모드에서 0/5 검색**이었어요. 즉 `tool_choice`는 양방향으로 무시돼요(F17과 일치). 검색 강제·금지는 게이트웨이에서 도구 목록을 빼거나 직접 호출해서 구현해야 해요.

### 3.2 prefill (질문 3, 질문 4)

콜드 prefill(캐시 미적중, 시스템 프롬프트에 임의 접두어를 붙여 캐시를 피함):

| 도구 수 | 프롬프트 토큰 | prefill |
|---|---|---|
| 0 | 926 | 1.98초 |
| 2 | 1282 | 2.64초 |
| 5 | 1671 | 3.46초 |
| 10 | 2316 | 4.99초 |
| 20 | 3608 | 7.96초 |

| 시스템 프롬프트에 붙인 메모리 글자 수 | 프롬프트 토큰 | prefill |
|---|---|---|
| 3,000 | 3,355 | 7.27초 |
| 9,000 | 7,504 | 19.1초 |
| 18,000 | 13,729 | 43.3초 |

- 도구 1개당 약 0.3초 prefill 증가(2→20개: +5.3초). 도구 정의 크기보다 **메모리/시스템 글자 수가 훨씬 지배적**이에요.
- 프롬프트 캐시: 전체 접두어 적중 시 0.2–0.28초. 큰 접두어가 캐시된 상태에서 도구 블록만 2개→5개로 바꾸면 2.05초(같은 길이 콜드는 19.4초). 도구 목록이 바뀌어도 접두어 일부는 재사용되지만 공짜는 아니에요.

### 3.3 요청별 thinking 끄기 (질문 2)

6회씩 측정(max_tokens 4096, `tools` 포함):

| 방식 | 중앙 지연 | 중앙 completion 토큰 | reasoning 비어있지 않음 |
|---|---|---|---|
| 기본(thinking on) | 8.4초 | 386 | 6/6 |
| 사용자 메시지에 `/no_think` | 1.59초 | – | reasoning 2자 |
| `chat_template_kwargs.enable_thinking=false` | 1.53초 | 62 | 0/6 |

요청별 kwargs가 현재 서버에서 **동작해요**. 정확도 영향은 §1의 V2 thinking on 79.4% → V3 73.5%(−5.9%p, 신뢰구간이 겹쳐서 단일 실행으로는 구분이 어려워요).

### 3.4 스트리밍과 `max_tokens` (질문 8)

- 스트림에서 도구 호출은 **인자가 완성된 JSON 한 덩어리**(id, index 포함)로 한 번에 와요. 점진적 인자 스트림은 없어요. 호출 앞 텍스트는 약 2자. 첫 청크 0.3–0.5초, 요청 전체 1.2–1.6초.
- 호출이 있는 요청의 completion 토큰: thinking off 중앙 47–51, 최대 97–101. thinking on 중앙 약 250, 최대 803(전체 요청 최대 2,254). 이번 측정에서 `max_tokens` 8192에 잘린 요청은 0건이에요. 결정 라운드에 thinking off를 쓰면 `max_tokens` 256이면 충분해 보이고(최대 101), thinking on이면 1,024 이상이 필요해요(호출 요청 최대 803).

### 3.5 큰 도구 결과 뒤 답변 라운드 (§4.3.3, §4.6)

큰 `web_fetch` 결과를 넣은 뒤 첫 출력까지의 시간(합성 한국어 채움 텍스트, Qwen3 토크나이저 실측: 6,000자=4,149토큰, 12,000자=8,298토큰, 24,000자=16,596토큰):

| 도구 결과 글자 수 | 토큰 | 첫 출력까지 |
|---|---|---|
| 0 | – | 3.1초 |
| 6,000 | 4.1k | 12.7초 |
| 12,000 | 8.3k | 26.4초 |
| 24,000 | 16.6k | 63.8초 |

시간은 결과 길이에 대해 선형보다 빠르게 늘어요. 설계의 "검색 후 첫 토큰 p95 ≤12초"는 **한국어 위주 결과라면 약 6,000자 안팎이 한계**예요. 24,000자 상한은 영문 위주라면 약 8k 토큰이지만 한국어 위주면 약 16.6k 토큰이라 64초가 걸려요. 결과 상한을 글자가 아니라 토큰(또는 한국어 기준 글자)으로 정하고, 현재 24,000자 상한을 낮추는 걸 제안해요. bge-m3와 리랭커가 올라와 있어도 같은 값이 나왔어요(12,000자 26.5초, 24,000자 64.2초).

### 3.6 임베딩/리랭커 동거 시 메모리와 :8080 속도 (질문 6, 질문 7)

bge-m3와 bge-reranker-v2-m3를 같은 호스트의 별도 프로세스(MLX)에 올려 놓고 측정했어요(`results/probe_embed_resident.json`).

- 두 모델 적재: MLX active 2,269MB, peak 4,534MB. 호스트 RAM 64GB, 서버(Python) 프로세스 footprint는 측정 전 18GB, 16.6k 토큰 prefill 이후 21GB(캐시 유지분).
- 큰 prefill 중 시스템 free 비율이 83–89% → 55–60%로 일시 하락했고, 스왑 사용량은 측정 전후 동일(1,633MB / 3,072MB)이라 **새 스왑 증가는 없었어요.**
- :8080 디코드 속도(생성 한 요청 기준):

| 조건 | 디코드 | TTFT | 전체 |
|---|---|---|---|
| 모델 적재, 유휴 | 42.0 tok/s | 0.2초 | 3.47초 |
| 인제스트 부하(32문서 배치 연속, op p50 455ms) | 31.5 tok/s (−25%) | 0.45초 | 3.85초 |
| 질의 부하(임베딩 1 + 리랭크 20 연속, duty 100%, op p50 201ms, n=310) | 12.6 tok/s (−70%) | 0.4초 | 9.41초 |

연속 duty 100% 최악 조건이라 실제 사용에서는 덜하지만, 질의 경로(임베딩+리랭크)가 생성과 겹치면 **생성 속도가 크게 떨어진다**는 점은 분명해요. 완화책으로 (a) 리랭크는 필요할 때만, (b) 후보를 20개보다 줄이기, (c) 생성 중에는 인제스트 배치를 미루기를 제안해요(완화책 효과는 아직 측정하지 않았어요).

유휴 시 연산 지연: 질의(임베딩 1 + 리랭크 20) p50 181.8ms, p95 192.8ms. 인제스트(32문서) p50 202.1ms, p95 219.9ms.

### 3.7 이번에 답하지 못한 질문
