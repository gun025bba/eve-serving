## 0. 요약

질문: 툴 선택 절차가 지금은 시스템 프롬프트로만 지켜진다. 프롬프트 밖에서 **시스템이** 강제할 수단이 무엇이고, 어느 것을 쓸 가치가 있는가.

| 후보 | 결정론적으로 보장하는 것 | 추천 (rev 2) |
|---|---|---|
| A. 게이트웨이 정책 검사 | 모델이 **볼 수 있는 툴**, 호출 **횟수·시간**, 인자의 **형태·출처 규칙**, 킬스위치 | **채택(안전 강제의 유일한 필수 박스).** 개정 4가 이미 담고 있다 |
| B. 출력 형식 강제 | 툴콜 JSON이 문법에 맞는 **모양**으로 나온다 | **보류.** 안전 보장이 새로 늘지 않는다. 실측 파싱 폴백 0건이라 트리거에서 더 멀어졌다 |
| C. 라우터 분리 | **호출 강제**를 gateway가 직접 실행(V4: 같은 모델의 한 단어 분류 + gateway 강제). 판정은 모델이라 확률적 | **재현율 강제 후보. 채택은 PM 결정.** 안전 강제는 하지 않는다. 지연·불필요 검색·원칙 충돌이 리스크(§2.3) |
| D. 검색어 검사기 | 쿼리의 **길이·시크릿 패턴·축어 겹침**(+ 사용자 메시지 출처 겹침 측정) | **A의 사전 점검 안의 함수로 채택.** 출처 겹침은 **그림자 지표로만** 먼저 |

### 0.1 이번에 바뀐 근거 (모델 엔지니어 실측, 이슈 #139)

요약만 적는다. 전문과 한계는 평가 결과 문서(`RESULTS.md`)에 있고, 표본이 작아(양성 68·음성 62, 변형당 1회 실행, 변형 간 5%p 안쪽은 노이즈) **방향을 정하는 근거이지 합격 판정이 아니다.**

| 사실 | 수치 | 이 메모에서의 의미 |
|---|---|---|
| 프롬프트만 쓴 변형의 재현율 | 최고 **80.9%**(V1 + thinking on, 95% 구간 70.0–88.5). thinking off 최고는 V3 73.5%. 기준(≥90%)에 못 미친다 | 프롬프트로는 P4(호출 여부)를 약속할 수 없다. 어느 프롬프트 전용 변형도 90%에 닿지 못했다 |
| V4: 같은 모델을 한 단어로 답하는 분류 게이트로 쓰고 gateway가 툴을 강제 | 재현율 **100%**(94.7–100), 불필요 검색 **6.5%**(구간 2.5–**15.4**) | 재현율은 충족. 불필요 검색은 점추정 6.5%가 기준(≤8%) 안이지만 **구간 상한 15.4%라 n=62로는 입증하지 못한다** |
| V4 지연 | 요청 전체 **중앙값 1.30초, p95 1.85초**(thinking off 요청별 kwargs, 워밍된 캐시, 짧은 프롬프트). 분류 호출 단독 추가분은 평균 0.39초(중앙값 0.36, p95 0.48) | 아래 §2.3의 지연 표기 주의 참조 |
| `mlx_lm`의 `tool_choice` | `auto`·`none`·`required`·지정을 각 5회 시도해 **양방향으로 무시**(양성 5/5 검색, 음성 0/5 검색) | **F17 "미검증" 해소.** 호출 강제·금지는 gateway가 도구 목록을 빼거나 직접 호출해서 해야 한다 |
| 요청별 thinking 끄기 | `chat_template_kwargs.enable_thinking=false`가 동작. 중앙 지연 8.4초 → 1.53초 | 결정 라운드의 지연 예산이 성립하는 전제 |
| 툴콜 파싱 | 모든 호출이 네이티브 `tool_calls`. 텍스트 `<tool_call>` 폴백 0건, 파싱 불가 인자 0건 | B(출력 형식 강제)의 트리거(파싱 실패율)가 현재 근거로는 걸리지 않는다 |
| V4 한계 | **측정만 했고 gateway에 통합한 end-to-end 측정은 아니다.** 오분류 음성 4건: injection 1, time_word_trap 1, url_given 1, conversation_memory 1 | 통합 전에는 지연·캐시·큐 영향을 모른다 |

### 0.2 핵심 추천 3줄 (rev 2)

1. **안전 강제는 여전히 A(gateway 사전 점검)가 맡는다.** 박스를 더하지 않고 Expose를 순수 함수로 둔 채 G1~G5를 표 기반 테스트로 못 박는다. D는 A 안의 함수이고, 출처 겹침은 그림자 지표로 먼저 잰다. B는 보류한다.
2. **재현율 강제는 V4 게이트가 현재 유일한 후보다.** 프롬프트만으로는 최고 80.9%(기준 90%)다. V4는 재현율 100%이고 별도 모델이 없다. 단 **채택은 PM이 결정한다**: 요청 p95 1.85초, 불필요 검색 6.5%(구간 상한 15.4%라 ≤8% 미충족), 개정 4의 "별도 분류기 없음" 원칙과 충돌, 불필요 검색이 곧 불필요한 외부 송출이다.
3. **채택하더라도 V4는 A 아래에 둔다.** 양성일 때만 호출을 강제하고(음성이면 툴은 그대로 노출해 모델이 결정, 오류 복구 가능), G1~G3·킬스위치·Budget이 V4보다 우선한다. 이 구조의 반영은 개정 4 문서의 개정 5(원칙 수정)에서 한다.

## 1. "강제"가 뜻하는 것

툴 선택 절차를 네 가지로 쪼개면 시스템이 결정적으로 강제할 수 있는 범위가 분명해진다.

| # | 절차 | 시스템이 결정적으로 강제 가능? | 현재(코드·설계) |
|---|---|---|---|
| P1 | **무엇이 노출되는가**(어떤 툴 정의를 모델에게 주는가) | 가능. 모델에게 안 보여 주고, 불러도 실행하지 않는다 | main은 모드·`web.enabled`로 노출. 개정 4는 Expose(G1~G3 포함) |
| P2 | **얼마나 부르는가**(횟수·시간·전역 예산) | 가능 | main: 라운드 3·호출 5·분당 한도(F5). 개정 4: 일일·전역 예산 추가 |
| P3 | **인자가 어떤 모양·출처인가**(길이, 시크릿 패턴, 에코, URL 출처) | 형태·축어 겹침은 가능. **의미(의역·번역)는 불가** | main: 256자 + `CheckQuery` 시크릿 패턴. 개정 4: 128룬, 4-gram 에코, URL 규칙 |
| P4 | **부를지 말지**(재현율·과호출) | 프롬프트로는 **불가**(실측 최고 80.9%). gateway가 호출을 **직접 실행**하는 것은 결정적으로 가능하지만(`tool_choice`는 서버가 무시하므로 gateway가 해야 한다), "필요하다"는 판정 자체는 모델이라 확률적이다(V4, §2.3) | 날짜·규칙 프롬프트, Gate 힌트, 평가 §8. V4는 후보 |

main(`b72651d`)의 `webChat`은 라운드마다 `tools`를 gateway가 만들어 보내고(`defs`), 모델이 낸 `tool_calls`는 gateway가 실행한다. 즉 P1~P3의 **집행 지점은 이미 gateway에 있다.** 프롬프트에만 기대는 부분은 (a) G2의 "쿼리는 사용자 메시지에서만"이라는 문구, (b) P4 전체다. 개정 4는 (a)를 라운드별 Expose와 사전 점검으로 옮겼다. 이 메모는 그 설계가 충분한지, 그리고 gateway 밖·모델 쪽에서 더할 만한 수단이 있는지를 따진다.

전제: **모델 출력은 요청이지 명령이 아니다.** 어떤 수단을 쓰든 gateway는 모든 툴콜을 다시 검증해야 한다(§6, 불변식은 모델·검사기에 의존하지 않는다). 아래 평가는 "gateway 검증을 대체하는가, 보태는가"를 기준으로 한다.

## 2. 후보별 검토

### 2.1 A. 게이트웨이 정책 검사

개정 4 §4.3의 Expose → 사전 점검(정규화 → CheckQuery → Echo → URL 규칙 → Budget) → Suspect 파이프라인 그 자체다. 이 메모에서의 추가 제안은 구조뿐이다: ① `Expose(상태) → 툴 정의`를 **순수 함수**로 둔다(상태 = 개인 데이터 읽음, 툴 결과 있음, fetch 읽음, suspect, 킬스위치, scope). ② 사전 점검 순서를 한 배열에 고정해 단계 추가·삭제가 코드 한 줄이고 테스트가 순서를 검증하게 한다.

| 항목 | 내용 |
|---|---|
| 결정론적 보장 | 같은 상태·같은 호출이면 같은 판정. 모델에게 보이지 않는 툴은 불러도 `denied`(P1). 횟수·시간·분당·일일·전역 한도(P2). 쿼리 128룬, 시크릿 패턴, 4-gram 에코, fetch URL은 사용자가 쓴 URL 또는 이번 턴 `sources`뿐(P3). 킬스위치는 진행 중 요청에도 다음 호출에서 차단(G4). 쓰기는 카드 |
| 한계 | **의미를 모른다.** 의역·번역된 쿼리, 사용자 메시지 자체의 민감 내용은 통과한다(잔여 위험 ①②). **호출 여부(P4)를 강제하지 못한다.** 노출을 줄이면 재현율이 깎이므로 G1~G3이 정한 라운드·상태 조건 밖에서는 숨기지 않는다. 상태 추적 버그가 곧 보장 구멍이 되므로 테스트가 필수 |
| 지연·비용 | 문자열 연산과 맵 조회뿐이라 호출당 µs~ms 규모로 **추정**(측정 아님). 지배 항은 Echo의 4-gram 집합 비교(보호 텍스트 P의 크기에 비례). 추가 모델·RAM 없음. 라운드 수는 늘지 않는다 |
| 복잡도 | 낮음. 새 서비스 없음. 이미 개정 4에 설계돼 있고 구현 이슈(#136~#141)가 있다. 코드는 `internal/tools`·`internal/handlers/web.go`에 얇게 들어간다 |
| 추천 | **채택.** 이 메모의 모든 다른 수단은 A 위에 얹는 선택이다. A만 있으면 P1~P3의 결정적 강제는 끝난다 |

### 2.2 B. 출력 형식 강제 (constrained decoding)

생성 시점에 모델이 낼 수 있는 토큰을 제한해 툴콜이 형식에 맞게 나오게 하는 수단이다. 세 갈래로 나눠 본다.

| 갈래 | 내용 | 현재 사실 |
|---|---|---|
| B1. 로짓 프로세서 문법 | `mlx_lm`의 로짓 프로세서 훅(토큰별로 허용되지 않는 토큰의 로짓을 `-inf`)에 JSON 스키마·문법 매처(Outlines, xgrammar, llguidance 등)를 붙인다 | 훅은 있으나 서버에 문법 프로세서는 없다. 서버 밖 래퍼가 필요하고, **배칭 경로에서 제약이 첫 요청 뒤 조용히 사라진다는 보고**가 있다(mlx-lm 이슈 #1007 논의, 2026-09) |
| B2. `response_format`/JSON 스키마 | OpenAI 호환 필드로 스키마를 요청에 싣는다 | `mlx_lm.server`는 이 필드를 **조용히 무시**하는 것으로 보고돼 있다(같은 이슈, 2026-07). 우리 배포 버전에서 재확인이 필요하다. `tool_choice`는 모델 엔지니어의 실측으로 **양방향 무시가 확인됐다**(§0.1, F17 해소) |
| B3. Qwen3 네이티브 툴콜 | 채팅 템플릿의 `<tool_call>{"name","arguments"}</tool_call>` 형식과 서버·gateway의 파서 | **이미 쓰고 있다**(F3). 형식 위반은 gateway의 텍스트 폴백 파서가 받고 개정 4 §7이 **파싱 폴백 비율**을 센다(최종 파싱 실패 건수는 같은 지표에 더하자는 제안). **평가 v1에서는 폴백 0건·파싱 불가 인자 0건**이었다 |

| 항목 | 내용 |
|---|---|
| 결정론적 보장 | B1을 쓰면 툴콜이 문법에 맞게 닫히는 것(유효 JSON, 툴 이름이 노출 목록 enum, 인자 필드와 `maxLength`)을 디코딩 단계에서 보장할 수 있다. B2는 현재 서버가 무시하므로 보장 없음. B3은 "파싱 가능한 형태가 나오도록 유도"일 뿐 보장은 없다 |
| 한계 | ① **안전 보장이 새로 늘지 않는다.** gateway는 어차피 이름·스키마·길이를 검증하고 거부해야 하므로, B가 없어도 위반은 막힌다. B가 줄이는 것은 "형식 불량 → 재시도·파싱 실패"의 빈도뿐이다. ② 쿼리의 **내용**은 못 정한다(의역 유출 그대로). ③ **호출을 강제**하려면 툴콜 접두 문법이 필요한데 모든 턴이 호출이 되어 재현율이 아니라 정밀도를 깬다. 호출 강제는 문법이 아니라 gateway의 직접 호출(§2.3 V4)이 더 단순하다. 자유 텍스트와 툴콜의 합집합 문법이 필요해 설계가 어렵다. ④ Qwen3는 사고 텍스트와 툴콜이 섞여 나올 수 있어 문법이 복잡해진다 |
| 지연·비용 | **미측정.** 토큰마다 어휘 전체(Qwen3는 약 15만) 마스크를 계산하므로 디코딩 속도가 떨어질 수 있다. 문법 컴파일 비용은 스키마별 캐시로 줄일 수 있다. 배칭을 끄면 동시 요청 처리량이 줄어든다. 모델 엔지니어가 `:8080` 생성 속도 영향을 실측해야 한다(#98 측정 항목과 같은 방식) |
| 복잡도 | 높음. 서버 밖 래퍼를 host의 모델 서빙 프로세스에 심어야 한다 = **새 공급망 의존성**(핀·서명·보안 검토 필요), `mlx_lm` 업그레이드마다 호환 점검, 한국어 멀티바이트 토큰 경계 정합성. 서빙 프로세스는 gateway와 별개로 배포·재시작돼 롤백 단위가 늘어난다 |
| 추천 | **보류.** 트리거 = 개정 4 §7의 **툴콜 파싱 폴백·실패 비율**이 평가에서 정한 기준을 넘고, 프롬프트 보강과 gateway 1회 재시도로도 못 내려갈 때. 현재 실측은 폴백 0건이라 **트리거에서 멀다.** 그때도 범위는 "툴콜 구간의 문법 한정(이름 enum + 인자 스키마)"로 최소화한다. 도입 전에 먼저 할 일은 지금의 파싱 실패율을 **재는 것**이다 |

### 2.3 C. 라우터 분리 (평가 v1 근거로 재작성)

모델과 별도의 호출이 "검색 필요 여부"를 정한다. rev 1은 이를 가정 위에서 "채택 안 함"으로 평가했다. 평가 v1이 **V4**를 측정했으므로 실제 후보로 다시 쓴다.

**V4가 무엇인가.** 별도 모델이 없다. 같은 모델(Qwen3-30B-A3B-4bit)에 질문을 보여 주고 "검색 필요: 예/아니오"를 **한 단어로** 답하게 한 뒤, gateway가 그 판정에 따라 **툴을 직접 강제**한다(`tool_choice`는 서버가 무시하므로 gateway가 `web_search`를 직접 호출하거나 노출을 정한다). 따라서 V4는 **별도 모델이 없는, gateway 강제형 라우터**다. 이것이 rev 1의 "라우터 = 새 모델·RAM 추가" 가정과 다른 점이다: RAM은 늘지 않고, 늘어나는 것은 호출 한 번이다.

| 항목 | 내용 |
|---|---|
| 결정론적 보장 | **강제의 실행**은 결정적이다: 판정이 "예"면 gateway가 항상 호출한다(모델이 무시할 수 없다). 하지만 **판정은 모델 출력이라 확률적**이다(재현율 100%는 양성 68개에서의 측정이며 구간은 94.7–100). 또 호출이 안전 규칙을 우회하면 안 되므로 V4의 호출도 A의 사전 점검(Expose·G1~G3·Echo·Budget·킬스위치)을 그대로 거친다 |
| 효과(실측) | 재현율 100%(프롬프트 전용 최고 80.9%, 기준 ≥90%). 불필요 검색 6.5%(프롬프트 변형은 0–3.2%). 홀드아웃(양성 17·음성 17)에서는 재현율 100%, 불필요 검색 5.9%(1/17). 오분류 음성 4건: injection·time_word_trap·url_given·conversation_memory 각 1 |
| 한계 | ① **불필요 검색의 신뢰구간 상한이 15.4%**로 기준(≤8%)을 입증하지 못한다(n=62). ② V4는 **측정만** 했고 gateway 통합 end-to-end는 없다. ③ 분류 대상은 현재 웹 검색뿐이다(캘린더 항목 없음, 평가 그룹 D 미구성). ④ 변형당 1회 실행, 양성 68개라 합격 판정이 아니라 방향이다. ⑤ **불필요 검색 = 불필요한 외부 송출**: 사용자 메시지가 외부 검색엔진으로 나가는 비율이 늘어난다(잔여 위험 ①의 빈도 증가, 아래 리스크). ⑥ 오분류에 `injection`과 `conversation_memory`가 있어, 판정이 잘못되면 민감한 대화에서도 검색이 강제될 수 있다. 그래서 V4는 G1(개인 데이터 읽은 턴 검색 0)·G2보다 **아래**여야 한다 |
| 지연·비용 | **표기 주의**: 평가 문서가 말하는 수치는 두 가지다. ⓐ 분류 호출 단독 추가분: 평균 **0.39초**(중앙값 0.36, p95 0.48). ⓑ thinking off에서 호출 결정까지 **요청 전체** 중앙값 **1.30초, p95 1.85초**(워밍 캐시, 짧은 프롬프트). 이 메모는 지연 리스크를 **p95 1.85초(요청 전체 기준)**로 적고 분류 단독분은 별도로 적는다. 개정 4 §4.6의 결정 라운드 p95 ≤3초 안이다. **측정 안 된 것**: 큐 세마포어 대기(동시 요청 시 한 호출 추가), 분류 호출이 본 호출 prefill 캐시에 주는 영향(시스템 프롬프트가 길어 캐시가 깨지면 콜드 prefill은 훨씬 느리다. 도구 2→20개 +5.3초), thinking on 구성에서의 지연(중앙값 5.5초) |
| 복잡도 | 중간. 새 모델·서비스·RAM은 없다. 새 호출 경로 하나, 분류 프롬프트·버전 관리, 평가 세트 유지, 실패 시 폴백(분류 실패 = 강제 안 함), 새 관측 지표. **개정 4의 "별도 분류기 없음" 원칙과 충돌**(아래) |
| 추천 | **재현율 강제 후보. 채택은 PM 결정**(아래 리스크를 받아들일지). 안전 강제는 하지 않는다 — 안전은 A의 몫이다. 채택하지 않을 경우 프롬프트만으로는 90%를 약속할 수 없으므로 **재현율 기준을 낮추거나(평가 §8.3 판정 방식 변경) 출시 게이트에서 분리**해야 한다 |

**개정 4와의 충돌 (명시).** 개정 4 §8.2는 V4를 "gateway 분류기, 같은 모델로 한 단어, 비교용" 변형으로만 정의했고 채택하지 않았다. 이 메모가 다루는 것은 그 비교용 변형을 **운영 설계에 넣을지**다. `auto-tool-selection.md` 개정 4 §0·§3은 **"별도 분류기는 만들지 않는다"**를 현재 설계 원칙으로 둔다(근거: 분류기 오류가 복구되지 않는다, 박스 증가, 호출 +1). V4는 같은 모델이라도 **모든 턴에 분류 호출을 한 번 더 하는 분류기**이며 Gate의 계약(`Hint → {none, fresh}`, 양성 **힌트**만, 개정 4 §4.3 Gate)도 "힌트"에서 **"강제"**로 넓힌다. 따라서 V4를 채택하면 개정 4의 원칙·Gate 정의·§3 비교표·§4.3.3 예산(호출 수 계산)을 **개정 5로 고쳐야** 하고, 이 메모는 그 개정을 하지 않는다. rev 1이 말한 "오류가 복구되지 않는다"는 약점은 V4를 **양성일 때만 강제하고, 음성이면 툴을 계속 노출해 모델이 결정하게** 하면 사라진다(분류기 오류가 재현율을 지금보다 낮추지 못한다). 이 구조는 이 메모의 제안이며 평가 v1이 측정한 구성은 아니다.

**트리거와의 관계.** rev 1이 둔 트리거 "Gate 재현율 < 90%"는 평가 v1에서 **이미 충족됐다**(프롬프트 전용 최고 80.9%). 그러므로 남은 질문은 "필요한가"가 아니라 "V4의 비용(R1~R7)을 받아들일 것인가"이고, 이는 PM이 정한다. 한편 rev 1이 말한 두 번째 용도(쿼리 작성을 사용자 메시지만 보는 호출로 **격리**하는 것)는 V4와 별개이고 트리거(관측된 의역 유출)도 아직 걸리지 않았다.

### 2.4 D. 검색어 검사기

모델이 만든 쿼리를 실행 전에 검사하는 결정적 함수 묶음이다. 별도 서비스가 아니라 A의 사전 점검 중간 단계다. 현재·설계된 것과 제안을 구분한다.

| 구분 | 검사 | 상태 |
|---|---|---|
| 기존 | `CheckQuery`: 빈 문자열, 길이, 시크릿 패턴(키·토큰·이메일·`.ts.net`·사설 IP 등) | main에 있음(길이 256자) |
| 설계됨 | 128룬 상한(G2), 정규화(NFKC·은닉문자 제거, M-5), 4-gram 에코(G5), 중복 쿼리(`duplicate_query`) | 개정 4 §4.3.1·§4.3.3 |
| **제안(이 메모)** | **사용자 메시지 출처 겹침**: 정규화한 쿼리의 토큰(또는 2-gram) 중 현재 사용자 메시지 U에 **없는 새 어휘**의 개수·비율을 센다. 임계를 넘으면(게이트로 올린 뒤) 거부 | 신규, **그림자 지표**로 먼저 |

| 항목 | 내용 |
|---|---|
| 결정론적 보장 | 기존·설계분: 시크릿 패턴, 길이, 사적 텍스트의 **축어·난독화·분할** 복사. 제안분: 쿼리가 **사용자 메시지에서 오지 않은 정보를 얼마나 싣는가**의 상한. 의역된 사적 정보는 보통 새 어휘를 만들므로, 사적 텍스트가 U 밖에서 올 때(= 인젝션 경로, 잔여 위험 ②) 일부를 결정적으로 잡는다 |
| 한계 | 사용자 메시지 **안**의 민감 내용은 면제된다(U가 기준이므로, 잔여 위험 ①). **정상 재작성도 새 어휘를 만든다**: 한국어 질문을 영어로 검색하기, 시점("2026")·`time_range` 추가, 고유명사 표기 변환. 임계가 낮으면 재현율이 깎이고, 높으면 의미가 없다. 어휘 단위 비교는 한국어 조사·활용 변형에 약하다(4-gram 문자 단위로 보완 가능). 의역이 U의 어휘만 재배열하면 통과한다 |
| 지연·비용 | Echo와 같은 정규화·집합 연산 재사용. 호출당 µs~ms 규모 **추정**. 추가 모델·RAM 없음 |
| 복잡도 | 낮음. 기존 정규화 함수를 재사용하는 함수 하나와 지표 하나(그림자 모드는 개수·비율만 기록하고 쿼리 원문은 남기지 않는다. 개정 4 §6.4의 HMAC·해시 규칙 준수) |
| 추천 | 기존·설계분은 **채택(이미 A에 포함).** 제안분은 **그림자 지표로 먼저 도입**: 평가의 정상 쿼리 세트(QA의 한국어 질문 세트, 합성)에서 새 어휘 비율 분포를 재고, 인젝션 mock에서의 분리도를 본다. **게이트 승격 여부는 측정 뒤** 정하며 그 시점에 SemVer를 다시 판단한다(거부 동작 변경이므로 확신이 없으면 MAJOR) |

| **Budget** | 턴·분·일일·전역 한도, 15초 | ● 본체 | – 문법은 호출 수를 못 센다 | – | ◐ 128룬, 중복 쿼리 |
| **Gate** | 최신성 양성 힌트 | ○ 어휘 사전이 gateway 안에 있다(실측: 양성 80.9% 반응, 음성 22.6% 반응이라 힌트로만 쓴다) | – | ● **교체·확장 후보 = V4.** 단 힌트가 아니라 **강제**이므로 Gate 계약 변경(개정 5). 음성이면 툴을 숨기지 않는다 | – |
| **G1** 개인 데이터를 읽은 턴은 검색 0, fetch는 사용자 URL만 | 상태 기반 노출·거부 | ● 본체(상태 추적 + Expose + URL 규칙) | – | ✕→A가 우선. V4의 강제 호출도 G1에 걸리면 `denied`여야 한다(오분류 `conversation_memory` 대비) | – |
| **G2** 쿼리는 현재 사용자 메시지만, 128룬, 턴당 2회 | 라운드 1에서만 노출 | ● 노출 제한·횟수 | ◐ `query.maxLength`를 문법에 | ◐ 쿼리 작성을 사용자 메시지만 보는 호출로 격리(트리거 ②). V4가 호출을 강제할 때 쿼리를 누가 쓰는지는 미정(R6) | ● 길이·패턴 + **출처 겹침(그림자)** |
| **G3** fetch 연쇄 금지 | fetch 뒤 검색·fetch 노출 안 함, URL 허용 집합 | ● 본체 | – | – | ○ fetch URL 에코 규칙 |
| **G4** "웹 검색함 + 쿼리" 표시, 킬스위치 즉시 | 사전 점검 첫 단계 킬스위치, 표시는 UI 계약 | ● 킬스위치 재확인(진행 중 요청 포함) | – | – | – |
| **G5** 4-gram 에코 유지 | 축어·난독화 차단 | ◐ 사전 점검 순서 안에서 실행 | – | – | ● 본체(Echo는 검사기의 한 종류) |
| (참고) Suspect | 주입 의심 결과 처리 | ● 본체 | – | – | – |

읽는 법: 열 A는 **모든 행에서 본체이거나 실행 환경**이다. B는 어떤 게이트도 새로 보장하지 않고 같은 게이트를 이중화한다. D는 G2·G5의 구현 방식이다. 즉 **G1~G5(안전 게이트)를 닫는 데 A·D 외에 필요한 후보가 없다.** C(V4)는 G1~G5 어느 것도 보장하지 않고 **Gate 행(재현율)에만 기여**하며, G1·G2·G3 아래에서만 동작해야 한다.

## 5. 단순함 점검: 박스 하나하나가 필요한가

| 박스 | 필요한가 | 근거 | 없애면 |
|---|---|---|---|
| gateway 사전 점검(A) | **필수** | 모델 출력을 신뢰하지 않는다는 불변식이 사는 유일한 곳. 다른 모든 수단이 있어도 이것은 남는다 | 불변식이 프롬프트·모델 준수에 의존하게 된다 |
| Expose를 순수 함수로 | 필수(이미 있는 단계의 형태 제안) | 테스트로 G1~G3을 표 기반으로 못 박는 수단. 코드 크기 증가 거의 없음 | 노출 규칙이 흩어져 검증이 어렵다 |
| 쿼리 검사기(D) | A의 함수로 필수 | 쿼리가 외부로 나가는 유일한 지점이다. 별도 서비스는 불필요 | 에코·시크릿 패턴 보호가 없다 |
| 출처 겹침 그림자 지표 | **조건부**(측정용) | 잔여 위험 ②를 줄일 결정적 후보가 이것뿐이라 값이 있는지부터 잰다. 코드는 함수 하나 | 승격 판단 근거가 없다 |
| 출력 형식 강제(B) | **불필요(지금)** | gateway 재검증이 있으므로 안전 보장이 겹친다. 실측 파싱 폴백 0건이라 줄일 문제도 없다 | 지금 설계(폴백 파서 + 재시도)로 충분 |
| V4 게이트(C) | **조건부, PM 결정** | **재현율이라는 별개 문제**를 푸는 유일한 실측 후보(프롬프트 최고 80.9% vs 100%). 안전 문제를 푸는 박스가 아니다 | 재현율 기준(≥90%)을 못 맞춘다. 기준을 바꾸거나 출시 게이트에서 분리해야 한다 |
| 별도 모델·임베딩 라우터 | **불필요** | 같은 모델 V4가 재현율을 충족했다. 별도 모델은 RAM 경합(#98)과 :8080 속도 저하(질의 부하 시 디코드 −70%)가 있다 | — |

결론: **안전을 위한 박스는 A(+D) 하나로 충분하다.** 재현율을 위한 박스는 V4가 후보이고 **채택은 PM 결정**이다. 둘은 목적이 다르므로 섞지 않는다.

## 6. 프롬프트에만 남는 것과 다루는 법 (P4)

"호출할지 말지"는 프롬프트로 90%를 약속할 수 없다(실측 최고 80.9%). 다음 순서로 다룬다.

1. **측정**: 자동 검색률, 불필요 검색 비율, 재현율을 평가 변형과 관측 지표로 본다(§7, §8). 표본이 작으므로 판정 방식도 함께 고친다: 프롬프트 동결 후 3회 이상, 양성 60개 이상의 새 홀드아웃, 불필요 검색은 점추정과 구간 상한을 함께 보고(모델 엔지니어 제안).
2. **힌트 보강**: Gate 어휘 사전·프롬프트 문구. 실측상 Gate 힌트의 효과는 구간이 겹쳐 구분되지 않는다(V1→V2). 이 단계만으로는 기준에 못 미친다.
3. **gateway 강제(V4)**: 위 두 단계로 재현율을 못 올릴 때의 유일한 실측 후보. **PM이 채택 여부를 정한다**(§2.3 리스크). 채택하면 안전 규칙(A) 아래에서만 동작하고, 음성이면 툴을 숨기지 않는다.
4. **사후 점검과 1회 재요청(청사진)**: Gate가 `fresh`인데 모델이 툴 없이 답한 경우 gateway가 한 번 재요청한다. V4보다 호출이 적게 늘지만 **스트리밍을 되돌릴 수 없다**: 툴이 있는 라운드는 비스트리밍(F7)이므로 가능하나 라운드 스트리밍(`streamRound`, §4.6) 도입 뒤에는 쓸 수 없다. V4를 채택하면 이 단계는 필요 없다.
5. **정직한 고지**: 검색이 실패했거나 하지 않은 최신성 질문은 `fresh:"unverified"`로 나가 UI가 알린다(개정 4 §13 Q3). gateway 규칙이라 프롬프트에 의존하지 않는다. V4 채택 여부와 무관하게 필요하다.

## 9. 열린 질문

1. **V4 게이트를 채택할 것인가 (PM 결정).** 필요한 입력은 §2.3 리스크 표다. 특히 R3(불필요 검색 = 외부 송출 증가)은 건영이 수용한 잔여 위험의 범위와 관련되므로 **보안 담당이 수용 범위가 V4를 포함하는지 판단**하고, 필요하면 PM이 건영에게 다시 확인한다. 채택 시 개정 4의 "별도 분류기 없음" 원칙과 Gate 정의를 고치는 **개정 5**가 필요하다(시스템 아키텍트). 채택하지 않으면 재현율 기준(≥90%)을 낮추거나 출시 게이트에서 분리해야 한다.
2. **재현율 기준 판정 방식**: 평가 문서는 "프롬프트 동결 후 3회 이상, 양성 60개 이상 홀드아웃, 경계 성향 카테고리 분리 보고"를 제안한다. PM·모델 엔지니어가 받아들일지 정한다.
3. **출처 겹침 그림자 지표를 개정 4 구현 이슈 범위에 넣을지**(어느 이슈에 둘지는 PM). 보안 담당: 그림자 모드가 "개수·비율만" 남기는 방식이 §6.4 규칙에 맞는지 확인 요청.
4. **사후 점검 재요청(§6 4단계)**: V4를 채택하면 불필요하다. 채택하지 않으면 스트리밍 설계(§4.6)와 함께 정한다.

SemVer: 이 문서 자체는 docs 변경이다(버전 영향 없음). 문서가 말하는 A·D 기존분은 개정 4의 MAJOR 출시 범위 안이다. 그림자 지표는 추가만 하는 관측이라 MINOR로 보되 **출처 겹침을 거부 게이트로 승격하는 것은 그 시점에 다시 판단한다**(확신이 없으면 MAJOR). **V4 채택은 모든 턴에 호출이 하나 늘고 외부 송출 빈도가 바뀌는 동작 변경이므로 개정 5에서 판단하며, 확신이 없으면 MAJOR로 본다**(이미 MAJOR 출시에 포함시킬지, 별도로 낼지는 PM).
