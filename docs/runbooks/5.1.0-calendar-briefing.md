# 5.1.0 — 캘린더 연동·아침 브리핑 (M1): switches, defaults, enabling

Everything in this feature is **off by default**. Merging or installing it changes nothing a user can see
until the owner turns a switch on, and turning the write switch on is an **external sync** (see below).

## The five gateway keys

| Key | Default | What it does | Needs |
|---|---|---|---|
| `GW_PIM_ENABLED` | `false` | Server switch for the read tools (`calendar_list_events`, `reminders_list`). Invalid value = start fails. | `GW_PIM_SOCKET_PATH` (absolute) and `GW_PIM_OWNER_USER_ID` (> 0) or the gateway refuses to start |
| `GW_PIM_SOCKET_PATH` | empty | The eve-pim helper's unix socket (absolute path). | helper running as the owner, socket dir 0750 group `_evepim` |
| `GW_PIM_OWNER_USER_ID` | `0` | The one `users.id` whose Calendar the tools may read. | integer > 0 |
| `GW_BRIEFING_ENABLED` | `false` | Server switch for the morning briefing preview (`POST /v1/briefing/preview`). No scheduler in 5.1.0. Invalid value = start fails. | owner opt-in per user (`PATCH /v1/settings`) |
| **`GW_PIM_WRITES_ENABLED`** | `false` | Lets the owner's model **propose** `calendar_add_event`, `reminders_add`, `reminders_complete`. Proposals are only confirmation cards. Ignored unless `GW_PIM_ENABLED=true`. | helper started with `--writes-enabled` (second, independent switch) |

None of these can be set through `/v1/settings` or `/admin/config`; they are environment (or `pim:` / `briefing:` config) only.
`install-calendar-adapter.sh` writes `GW_PIM_ENABLED=false`, `GW_PIM_WRITES_ENABLED=false` and `GW_BRIEFING_ENABLED=false` if they are absent and never sets anything to `true`.

### Adapter installer (`deploy/install-calendar-adapter.sh`): verify and install only, no build on the Mac

> **STATUS: the installer refuses every install (`PIM_PIN_READY=0`) until the pin moves.** `PIM_SHA` is still `6ce1993`, the commit
> **before** the source this PR adds (`pim/eve-pim/build-release.sh`, the calendar-only `Support/` files, the launchd template). A binary built
> from `6ce1993` cannot pass the installer's rules, and a manifest that names `6ce1993` for a binary built from other source would certify the
> wrong provenance (security review M-1). So: **the pin moves in a separate deploy-major change after this source is merged** (set `PIM_SHA` to the
> merged commit, move `keep/pim-adapter-*` with it, set `PIM_PIN_READY=1`; security re-approval, rollback plan and control-plane approval as
> for any major). **Until that change is deployed the adapter must not be signed or installed.** `sign-pim-manifest.sh` also refuses to sign
> while the pin is not ready (only `--test-only`, which the installer still refuses). Once `PIM_PIN_READY=1`, `go test ./internal/deploycheck`
> requires `PIM_SHA` to contain `pim/eve-pim/build-release.sh` and the `Support/` files and to be an ancestor of HEAD (the job needs full git
> history: `fetch-depth: 0`).

CI builds and signs the adapter; the script only **verifies and installs** it. There is no `git clone`, no `swift` and no
`EXP_PIM_SHA256` any more (nothing is compiled as root, nothing is pinned by hand after a first build).

```
sudo bash install-calendar-adapter.sh --manifest <abs>/eve-pim.MANIFEST --sig <abs>/eve-pim.MANIFEST.sig --adapter <abs>/eve-pim
sudo bash install-calendar-adapter.sh --rollback
```

The install is a manual step by the owner (it needs `sudo` and a GUI session for the TCC prompt): the first install and every release that changes
`PIM_SHA` or the adapter's sha256. Normal deploys never touch the adapter, and no sudoers verb is added for it.

**Inputs (three files, absolute paths, staged by the login user, e.g. in `/usr/local/libexec/eve/staging`).** They are copied
into the private root-only work dir first; every check judges the copy, never the staged original.

| Input | Content |
|---|---|
| `eve-pim` | the CI-built adapter, ad-hoc signed with the hardened runtime (`codesign -s - -o runtime`) |
| `eve-pim.MANIFEST` | exactly three lines: `eve-pim-manifest=1`, `pim_sha=<40 lowercase hex>`, `pim_sha256=<64 lowercase hex>` (any order, no duplicates, no other line, no NUL) |
| `eve-pim.MANIFEST.sig` | today: `ssh-keygen -Y sign`, namespace `eve-deploy`, of the manifest bytes, verified by the deploy entrypoint's `verify_sig`. **Production signing is not done with a local key:** it moves to a protected CI job with Sigstore keyless (cosign), see "What CI must provide" and "Constraints for the cosign switch". `deploy/nopasswd/sign-pim-manifest.sh` is for local use and tests only. |

**What must hold before anything is installed (all of it, otherwise nothing changes):**

0. The pin is ready (`PIM_PIN_READY=1`, see STATUS above); otherwise nothing runs.
1. The signature verifies against the release key pinned on the Mac. The script **sources the passwordless-deploy entrypoint**
   (`/usr/local/libexec/eve/deploy`, root-owned) in a subshell and calls its `verify_sig`: same pinned `allowed_signers`, same namespace
   and identity, no second trust root, **no new sudoers verb**. There is no test hook in the installer; tests run the same function against a
   copy of the entrypoint whose trust root is a temp dir. A refused signature logs one short reason line.
2. `pim_sha` is the 40-hex `PIM_SHA` pinned in the script (the security-reviewed source commit; a signed manifest for another commit is refused)
   and has the exact format (a short ref, upper case, 39/41 characters or any extra text is refused).
3. `sha256(adapter) == pim_sha256`.
4. The adapter's code signature is valid, carries the hardened runtime flag, **only** the entitlement
   `com.apple.security.personal-information.calendars`, and **only** the usage strings `NSCalendarsUsageDescription` /
   `NSCalendarsFullAccessUsageDescription` (no contacts, no Reminders, no full disk access, nothing else).

**Install.** Fixed root-owned target `/opt/eve-pim/bin/eve-pim` (`root:wheel`, `0755`; `/opt/eve-pim` and `/opt/eve-pim/bin` must be real,
root-owned and not group/world writable; **every parent up to `/` is checked the same way**, as is the verifier's directory). The new file is written next to the target (same directory, `root:wheel 0755`), hash-checked,
moved over the old one with one atomic `mv`, and its sha256, owner and mode are checked again afterwards. If any step fails the previous
adapter and its signed record are put back (or the unverified file is removed on a first install) and the script stops. The hardened-runtime
check reads the `CodeDirectory ... flags=0x...(...)` line only: exactly one such line, the flag name `runtime` in its list and the numeric
bit `0x10000` (a path or another line containing the word does not count). The work directory's input copies and backups are deleted when the
script exits; only the log stays in the private `/tmp/eve-install-calendar-adapter.*` directory.
The login user's home is no longer an execution location (`~/eve-pim` from the old local build is unused; the script says so, delete it by hand).

**Same hash = no-op.** If the installed binary already has `pim_sha256` (and the right owner/mode) it is **not replaced**, so the code
signature (cdhash) and the TCC grant stay untouched and macOS does not prompt again. A new build (different sha256) prompts for Calendar once.
Moving from the old `~/eve-pim` to `/opt/eve-pim/bin` is a new path and a different binary, so that first install prompts once as well.

**No rollback, no upgrade (fail closed).** Replacing an installed adapter needs a verified rollback target: the installed adapter must match its own signed
record (`eve-pim.manifest` + `.sig`, signature valid, sha256 equal). If there is no such record, or the previous adapter cannot be kept, the script
**refuses the upgrade and changes nothing**. The first install has nothing to roll back to and is allowed. If you knowingly accept having no rollback, stop the
helper and remove `/opt/eve-pim/bin/eve-pim` by hand, then install again.

**Rollback.** Each upgrade keeps exactly one previous adapter next to the target (`eve-pim.prev`, with its own signed manifest and signature, `0755 root:wheel`),
only when the installed adapter matches its own signed record. `--rollback` follows the install rules: the kept manifest signature is
verified again, its `pim_sha256` must match the kept binary, the code-signature rules apply, the swap is atomic, the hash is verified
afterwards (the expected sha256 of the binary, manifest and signature is passed down to the swap, so a file changed after its checks is not installed),
an identical hash is a no-op, and a failed rollback restores the state before it. It is one step only (the kept previous is
consumed); there is no second rollback.

**Calendar only; Reminders are not requested.** The helper no longer asks for Reminders access at start-up (a Reminders request without a
Reminders usage string terminates the process on macOS, and the approved plist and entitlements are calendar-only). `reminders_list`,
`reminders_add` and `reminders_complete` therefore answer `permission_denied` until a separate, security-reviewed change adds Reminders back.

**Pins.** `PIM_SHA` must be the full 40-hex commit CI built from. The commit stays reachable on branch `keep/pim-adapter-6ce1993`
(do not delete it; no tags). When the pin moves, move that branch (fast-forward) together with `PIM_SHA` and the CI build.

**What CI must provide per build** (two separate jobs, owned by the CI change, not by this PR):

1. **Build job (macOS runner). The build job holds no secrets.** Permissions `contents: read` only, actions pinned to a commit SHA, no `pull_request_target`,
   no fork PRs, and it builds only when `github.sha == PIM_SHA`. It runs `pim/eve-pim/build-release.sh --out <dir>` (hardened-runtime ad-hoc signature with
   `pim/eve-pim/Support/eve-pim.entitlements` and the embedded `Support/eve-pim-Info.plist`) and uploads `eve-pim` as an artifact. It never sees a signing key or a token.
2. **Sign job (separate, protected: environment with required approvers).** It downloads the artifact, computes the sha256 itself, writes the 3-line manifest
   (`eve-pim-manifest=1`, `pim_sha`, `pim_sha256`) and signs it with **cosign keyless** (Sigstore). `id-token: write` is granted to the signing step only. Nothing
   in Actions secrets: **the deploy release key is never put into CI.**
3. Publish `eve-pim`, `eve-pim.MANIFEST` and the signature bundle. Until the cosign verification replaces `verify_manifest_sig` (DevOps's change), the installer
   still verifies the `ssh-keygen` signature of the deploy entrypoint; `sign-pim-manifest.sh` (**local use and tests only**, never in CI) exists to produce that format in tests.

**Constraints for the cosign switch** (security review §6; DevOps's change must keep all of them):

- No local-key path in production: remove `ssh-keygen` / `allowed_signers` verification of the manifest completely, **no fallback**. A Go test pins "no `ssh-keygen`, no fallback, no hook in the production script".
- Fixed in code (not by environment or arguments): an absolute-path, root-owned cosign binary (version and sha256 pinned, no `PATH`), a cleaned environment (`env -i`: ignore `COSIGN_*`, `SIGSTORE_*`, proxy variables),
  `--certificate-identity` (workflow file path + ref, exact), `--certificate-oidc-issuer` (the GitHub Actions issuer, exact), the repository, and `--certificate-github-workflow-sha` equal to `PIM_SHA`
  (binds `pim_sha` to the certificate). `--insecure-ignore-tlog` and `--insecure-ignore-sct` are forbidden; the trust root is pinned or the check fails closed.
- Offline and re-verifiable: the signature **bundle** (signature + certificate + Rekor proof) is the input and is verified offline; the **rollback record keeps its bundle too**, so a rollback passes the same check after the short-lived certificate expired (tlog time).
- Kept as is: subshell verification and fail-closed, judging only root-owned copies, the strict 3-line manifest, 40 lowercase hex `pim_sha`, `pim_sha256` comparison, same hash = no-op, atomic rename + re-verify + restore, the codesign allow-lists, one rollback step with the same rules, no new sudoers verb, no host or secret in logs.
- CI: `id-token: write` only on the signing step; sign only on the `PIM_SHA` commit; protected environment; the sign job computes the artifact hashes itself. A change of the workflow identity (path) is a deploy-major change.
- Tests to add there: other identity, other issuer, other workflow sha, missing bundle, bundle after certificate expiry, tampered manifest: all refused.
- Deferred to that switch (security review L-2): today the manifest signature shares the key and namespace (`eve-deploy`) with the deploy bundle; the formats differ (3-line manifest vs tar) so they cannot be swapped, but there is no domain separation. The certificate identity separates them once cosign is in.

**Classify rule (what counts as deploy-major).** The deploy classifier is **not in this repository on `release/5.1.0`**; it belongs to DevOps's unattended-deploy change (#144).
It must treat as **deploy-major** (and, if it cannot tell, as major): any change of `PIM_SHA`, of `PIM_PIN_READY`, of the adapter's sha256 or manifest, of the cosign identity/issuer (workflow path), of the allowed entitlements/usage keys,
and of `deploy/install-calendar-adapter.sh`'s trust constants. Until that classifier exists and has a test for it, a reviewer applies this rule by hand (and "when unsure, major", `docs/versioning.md`).

**Tests.** `deploy/test-calendar-adapter.sh` (run by `go test ./internal/deploycheck` and by `deploy/nopasswd/test/run.sh`, so also on the macOS runner with bash 3.2) covers hash mismatch,
bad `pim_sha`, bad signatures, code-signature/entitlement/usage-key rejection, same-hash no-op, atomic install, failed rename, post-install re-verify and the rollback rules.

The inputs' copies and the log live in a private `mktemp -d` directory under `/tmp` (mode 0700); no predictable path is created by root. The copies are removed on exit.

## Writes are an external sync — owner approval required

An event created by `calendar_add_event` (and a reminder created or completed) is written to the Mac's
Calendar/Reminders, which sync to the linked accounts (iCloud, Exchange, Google). Turning on **both**
`GW_PIM_WRITES_ENABLED=true` **and** the helper's `--writes-enabled` therefore needs the owner's explicit approval.
Neither flag is set by any install or deploy script.

What the owner sees before anything is written:
- The model only creates a card. Nothing is written until the owner approves it in a browser session
  (`interactive` scope; an API key gets 403).
- `calendar_add_event` **requires `calendar_id`** (taken from a `calendar_list_events` result, a writable calendar).
  The card always shows that calendar's name next to the exact title, time, place and notes. There is no
  "default calendar" path, so the target of the sync is never implicit (review finding L-1).
- Approve re-validates the card, re-checks the flags and that the calendar is still writable, writes the audit row
  (hash only) and makes exactly one helper call. An unknown outcome is not retried (no idempotency key in EventKit).

## Data left behind, and its cleanup

- Event/reminder text of a card lives in `pending_actions.payload` and `payload_view` while the card is open.
  A job in the gateway (every 6 h, also at start) blanks both to `{}` for finished pim write cards
  (approved, rejected, voided, expired) 24 h after they ended. `payload_hash` and the status stay. It runs even
  when pim is switched off, so cards from an earlier period are still cleaned up.
- Logs and audit rows carry only the method, a count, an error code and the payload hash — never event content.

## Limits worth knowing

- Titles shown to the model or put in the briefing are cut to 200 characters (`…`).
- Text fields refuse control characters, zero-width/format characters and U+2028/U+2029 (gateway and helper use the same rule).
- The helper answers one request per connection and gives up on a request that has not fully arrived 3 seconds after it connected.

## Turning things on (owner only), in this order, one at a time

1. Reads: set `GW_PIM_SOCKET_PATH`, `GW_PIM_OWNER_USER_ID`, then `GW_PIM_ENABLED=true`; approve the **Calendar** (TCC) prompt once (Reminders is not requested). Check with a chat question about today's events.

   **An unexpected TCC prompt is never "Allow".** The only prompt that may appear is "eve-pim would like to access your calendar". Anything else (Reminders, Contacts,
   Photos, files, another app name or path, a second prompt out of the blue) means: choose **Don't Allow**, **PAUSE** (stop the helper:
   `launchctl bootout gui/$(id -u)/com.eve.pim`; do not re-run the installer), check `ls -l /opt/eve-pim/bin/eve-pim` and `shasum -a 256 /opt/eve-pim/bin/eve-pim` against the signed
   manifest's `pim_sha256` (and that the path is exactly `/opt/eve-pim/bin/eve-pim`), and tell security before continuing. The installer prints the same instructions.
2. Briefing: `GW_BRIEFING_ENABLED=true`, then the owner's own opt-in in settings. Preview only.
3. Writes (needs separate explicit approval, see above): `GW_PIM_WRITES_ENABLED=true` and the helper LaunchAgent with `--writes-enabled`.

Undo is the same keys back to `false` (and, for the helper, removing `--writes-enabled`); no data migration is involved.
