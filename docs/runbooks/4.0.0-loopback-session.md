# Runbook: gateway 4.0.0, TCP loopback + browser sessions + dedicated `_evegw` user

Design: `docs/architecture/identity-transport.md`. Replaces the unix-socket plan (the socket target 502s under the
sandboxed macOS Tailscale).

Status: **not executed**. 건영 runs the `sudo` steps himself. The agent can run only steps marked *(no sudo)*.
Why: before 4.0.0, `127.0.0.1:8000` trusted `Tailscale-User-Login` from any local process (security review: HIGH).
In 4.0.0 **no request header is identity**. Every request except `GET /health` and `POST /v1/pair` needs a browser
session cookie (`eve_session`, from a one-time pairing code) or the API key (`Authorization: Bearer`).
`Tailscale-User-*` headers are stripped and only logged (`ts_login_hint`). The gateway listens on TCP
`127.0.0.1` (or `::1`) only and refuses any other bind address.

**Every existing browser must re-pair after cutover** (§5): old 3.x browsers have no session cookie and get 401.

Placeholders: `<TS_HOST>` = the Mac's ts.net name, `<ME>` = 건영's macOS login, `<login>` = an `allowed_users` entry.
Never paste secrets into a shell history line. Use an editor on the 0600 files instead.

## 0. Decisions

| Item | Decision |
|---|---|
| Service user | `_evegw` (hidden, no login shell, own group `_evegw`) |
| Layout | `/opt/eve-gw`, `bin/`, `web/` and the binary: **root:wheel 0755** (files 0644/0755), so `_evegw` cannot modify its own code. `_evegw` owns only `etc/` (0700) and `log/` (0750) |
| `_evegw` group | **Never add humans or agents to `_evegw`.** Group membership would expose `etc/` secrets if a mode is ever loosened. Check: `dscl . -read /Groups/_evegw GroupMembership` must print nothing / no such key |
| Launch | `/Library/LaunchDaemons/com.llmserving.gateway.plist` with `UserName=_evegw`. The old LaunchAgent is removed |
| Secrets | DB URL, API key and session pepper go in `/opt/eve-gw/etc/` (0600 `_evegw`), **not** in the plist. After cutover both are **rotated** (§9) and the old copies are deleted (with 건영's confirmation) |
| Backups | `backups/*.dump` and anything holding secrets: `root:wheel 0600` (or age-encrypted, plaintext removed) |
| `tailscale serve` | `https:443 / -> http://127.0.0.1:8000`. Funnel stays off. Every serve command runs with `sudo`; operator is cleared (§5) |
| TCP `:8000` | The only listener, `127.0.0.1` only (startup refuses anything else). Browsers authenticate with a session cookie, scripts with the API key. `allowed_hosts` must list `<TS_HOST>` (Host allowlist; others get 421) |
| Sessions | Pairing code 8 chars (`XXXX-XXXX`), 10 min, one use. 5 failed pair attempts lock pairing for 10 min and void outstanding codes. Session idle 30 d, absolute 180 d. Codes/tokens stored only as HMAC-SHA256 with the pepper |
| pf | Optional. See §5 |

macOS ships openrsync, which has no `--chown`, so the UI is copied with `cp -RP` (never follow symlinks) + `chown`/`chmod` instead of `rsync --chown`. The source `web/` is checked with `find -type l` first and the copy is not run if it prints anything.
Startup refuses an API key file or pepper file with any group/other permission bit (must be 0600 or stricter).
Changing the session pepper invalidates every session and pairing code: all browsers must re-pair (`gateway pair`). A rotation procedure is backlog (#59).
In that editor:
- `log_file: /opt/eve-gw/log/gateway.log`
- `static_dir: /opt/eve-gw/web`
- `database.url:` paste the current `GW_DATABASE_URL` value from the old plist. Copy it in the editor; don't echo it.
- `session_pepper_file: /opt/eve-gw/etc/session_pepper`
- `allowed_hosts: [<TS_HOST>]` (localhost/127.0.0.1/::1 are always allowed)
- Remove `unix_socket` / `tcp_disabled` and any `tailscale-identity` provider if present: 4.0.0 **refuses to start** with them.
- If a `tools_killswitch_file` is used, move it under `/opt/eve-gw/etc/` (0600). The kill switch requires the file to be owned by the gateway uid.

## 5. Point `tailscale serve` at TCP loopback and re-pair browsers **(sudo: 건영)**
**What this Mac runs** (checked read-only on 2026-10-27): the standalone **macsys GUI app** 1.104.2, not the
open-source `tailscaled`.
- `/usr/local/bin/tailscale` is a 2-line shim that runs `/Applications/Tailscale.app/Contents/MacOS/Tailscale`.
- The daemon is the system extension `io.tailscale.ipn.macsys.network-extension`, running as root.
- The GUI app runs as 건영's login, and the agent runs as that same macOS account.
- `tailscale debug prefs` shows **no `OperatorUser` set**.

**How `--operator` behaves here:**
- `--operator` is the `tailscaled` (Linux and similar) mechanism for letting a non-root user change prefs and serve.
  On the macsys app, the logged-in GUI user gets LocalAPI access through the app regardless of operator.
- So `sudo tailscale set --operator=` is a harmless no-op on this Mac. Run it anyway, so the state is explicit and
  stays correct if the Mac ever moves to `tailscaled`.
- **Residual risk:** the agent's account is the console user, so it can still run `tailscale serve` without sudo.
  It could point serve at a listener it controls. It cannot mint identity at the gateway (headers carry none),
  but it could proxy or phish the UI.
- Mitigations: the agent's rules forbid serve changes (they need 건영), and §9 includes a `serve status` check.
  The real fix is running the agent under a separate macOS account; that is out of scope here.

```sh
sudo tailscale set --operator=                       # clear operator (no-op on macsys, explicit for tailscaled)
sudo tailscale serve --https=443 off
sudo tailscale serve --bg --https=443 http://127.0.0.1:8000
sudo tailscale serve status    # https://<TS_HOST> (tailnet only) |-- / proxy http://127.0.0.1:8000
EXPECT=http://127.0.0.1:8000 scripts/check-serve.sh   # (no sudo) must print OK
sudo tailscale funnel status   # must show no funnel
```
If `sudo tailscale ...` errors (for example, the GUI shim refuses to run as root), run the same serve lines without
sudo from 건영's own Terminal. Do not let the agent run them.

Re-pair every browser (each existing browser **must** do this once; 3.x browsers get 401 until then):
```sh
sudo -u _evegw /opt/eve-gw/bin/gateway pair -config /opt/eve-gw/etc/config.yaml --user <login>   # (sudo: pepper + DB URL are _evegw 0600) prints XXXX-XXXX
```
Open `https://<TS_HOST>/ui` on the device within 10 minutes and enter the code. The code works once.
List / revoke sessions: `sudo -u _evegw /opt/eve-gw/bin/gateway sessions list -config /opt/eve-gw/etc/config.yaml` and `... sessions revoke <id>`.

Smoke test:
- After pairing, the UI loads threads as `<login>`, sends a chat and saves it.
- On the Mac, a forged header must return **401**:
  ```sh
  curl -s -o /dev/null -w '%{http_code}
' -H 'Tailscale-User-Login: <login>' 127.0.0.1:8000/whoami
  ```
- A wrong Host must return **421**: `curl -s -o /dev/null -w '%{http_code}
' -H 'Host: evil.example' 127.0.0.1:8000/health`.
- With the API key, `/whoami` must report `"user":"api-key"`.
- `sudo tail /opt/eve-gw/log/gateway.log` shows `"auth_provider":"session"` for UI requests.

### Optional pf rule **(sudo: 건영)**
This is defense in depth. Only `_evegw` and 건영 may open TCP connections to 127.0.0.1:8000.
- macOS pf `user` matching applies to sockets owned by local processes.
- Test it first with `sudo pfctl -vnf`.
- macOS updates can reset `/etc/pf.conf`; re-check after updates.
```sh
printf 'pass  out quick on lo0 proto tcp from any to 127.0.0.1 port 8000 user { _evegw, <ME> }\nblock return out quick on lo0 proto tcp from any to 127.0.0.1 port 8000\n' | sudo tee /etc/pf.anchors/eve-gw
sudo cp -p /etc/pf.conf /etc/pf.conf.pre-eve
echo 'anchor "eve-gw"
load anchor "eve-gw" from "/etc/pf.anchors/eve-gw"' | sudo tee -a /etc/pf.conf
sudo pfctl -vnf /etc/pf.conf && sudo pfctl -f /etc/pf.conf && sudo pfctl -E
```
Remove it with `sudo cp -p /etc/pf.conf.pre-eve /etc/pf.conf && sudo pfctl -f /etc/pf.conf`.

## 10. Compensating controls for the accepted Med2 risk
The agent's account can still run `tailscale serve`; security accepted this as residual risk with two controls.

### 10a. Remove the funnel nodeAttr in the Tailscale admin console **(건영, browser; no sudo)**
State checked read-only on 2026-10-27: the node's `CapMap` has **no `funnel` capability**, serve has no
`AllowFunnel`, and `tailscale funnel status` says "tailnet only". So the policy already doesn't grant funnel to
this node. Keep it that way, and remove the attribute if it is ever added:
1. Go to admin console → **Access controls** (tailnet policy file).
2. In `"nodeAttrs"`, find entries whose `"attr"` contains `"funnel"` and whose `"target"` matches this node, its tag,
   its owner, `autogroup:member` or `*`. Remove `"funnel"` from that `attr` list, or narrow the target so it
   excludes this node. Save.
3. Verify on the Mac (read-only):
   ```sh
   tailscale status --json | python3 -c 'import json,sys;s=json.load(sys.stdin)["Self"];print([c for c in list(s.get("CapMap") or {})+(s.get("Capabilities") or []) if "funnel" in c] or "no funnel cap")'
   scripts/check-serve.sh      # also fails if a funnel capability appears
   ```
   With the attribute gone, `tailscale funnel 443 on` fails with a "Funnel not available" error. Don't run that
   on prod as a test.

### 10b. Scheduled serve check *(no sudo, read-only)*
`scripts/check-serve.sh` exits 0 only if all of the following hold:
- serve has exactly one handler, `/` → `$EXPECT` on HTTPS 443, with no other TCP, Services or Foreground config;
- funnel is off;
- the node has no funnel capability.

It exits 1 on any drift and 2 if it can't read the state.
```sh
EXPECT=http://127.0.0.1:8000 scripts/check-serve.sh   # before and after cutover (the serve target does not change)
```
Schedule it (cron/launchd, owner's choice). Treat a non-zero exit as an incident: someone changed serve.
