# Runbook: gateway 4.0.0, trusted unix socket + dedicated `_evegw` user

Status: **not executed**. 건영 runs the `sudo` steps himself. The agent can run only steps marked *(no sudo)*.
Why: before 4.0.0, `127.0.0.1:8000` trusted `Tailscale-User-Login` from any local process (security review: HIGH).
4.0.0 trusts identity headers only on a unix socket that only `tailscale serve` (root network extension) and the
gateway user can reach. Any process can still connect to TCP, but there it gets API-key auth only.

Placeholders: `<TS_HOST>` = the Mac's ts.net name, `<ME>` = 건영's macOS login. Never paste secrets into a shell
history line. Use an editor on the 0600 files instead.

## 0. Decisions

| Item | Decision |
|---|---|
| Service user | `_evegw` (hidden, no login shell, own group `_evegw`) |
| Layout | `/opt/eve-gw`, `bin/`, `web/` and the binary: **root:wheel 0755** (files 0644/0755), so `_evegw` cannot modify its own code. `_evegw` owns only `etc/` (0700), `run/` (0700) and `log/` (0750). `run/gw.sock` is 0660. Startup refuses a socket dir whose ancestors are not root/self-owned or are group/world-writable |
| `_evegw` group | **Never add humans or agents (including 건영's and the agent's account) to `_evegw`.** The socket is 0660 `_evegw:_evegw`, so group membership = the ability to assert any Tailscale identity. Check: `dscl . -read /Groups/_evegw GroupMembership` must print nothing / no such key |
| Launch | `/Library/LaunchDaemons/com.llmserving.gateway.plist` with `UserName=_evegw`. The old LaunchAgent is removed |
| Secrets | DB URL and API key go in `/opt/eve-gw/etc/` (0600 `_evegw`), **not** in the plist. After cutover both are **rotated** (§9) and the old copies are deleted (with 건영's confirmation) |
| Backups | `backups/*.dump` and anything holding secrets: `root:wheel 0600` (or age-encrypted, plaintext removed) |
| `tailscale serve` | `https:443 / -> unix:/opt/eve-gw/run/gw.sock`. Funnel stays off. Every serve command runs with `sudo`; operator is cleared (§5) |
| TCP `:8000` | **Keep it on 127.0.0.1, API key only** for phase 1. Identity headers are stripped there, which closes the HIGH. Local scripts, health checks and rollback keep working. Log audit (3.0.0 to 3.1.0): there was no API-key traffic on :8000. Phase 2, after 7 days with no `auth_provider=api-key` requests in the log: set `GW_TCP_DISABLED=true` (see §6) |
| pf | Optional. See §5 |

Or generate it from the old LaunchAgent with python `plistlib` (no sudo). It copies only an **allowlist** of `EnvironmentVariables` (anything else, e.g. `GW_DATABASE_URL` or stray secrets, is dropped) and prints key names only, never values:
```sh
python3 - <<'PY'

src = os.path.expanduser("~/Library/LaunchAgents/com.llmserving.gateway.plist")
with open(src, "rb") as f:
    old = dict(plistlib.load(f).get("EnvironmentVariables", {}))
ALLOW = {"GW_ENV", "GW_ALLOWED_ORIGINS", "GW_ALLOWED_USERS", "GW_DB_AUTO_MIGRATE",
         "GW_PUSH_ENABLED", "GW_WEB_ENABLED", "GW_SEARXNG_URL", "GW_UNIX_SOCKET"}
env = {k: v for k, v in old.items() if k in ALLOW}
print("dropped keys:", ", ".join(sorted(set(old) - ALLOW)) or "-")
env.update(GW_DB_AUTO_MIGRATE="false", GW_UNIX_SOCKET="/opt/eve-gw/run/gw.sock")
pl = {
    "Label": "com.llmserving.gateway", "UserName": "_evegw", "GroupName": "_evegw",
    "ProgramArguments": ["/opt/eve-gw/bin/gateway", "-config", "/opt/eve-gw/etc/config.yaml",
                         "-key-file", "/opt/eve-gw/etc/api_key", "-host", "127.0.0.1", "-port", "8000"],
    "EnvironmentVariables": env, "WorkingDirectory": "/opt/eve-gw",
    "StandardOutPath": "/opt/eve-gw/log/gateway.launchd.log",
    "StandardErrorPath": "/opt/eve-gw/log/gateway.launchd.log",
    "RunAtLoad": True, "KeepAlive": True, "ThrottleInterval": 15,
}
fd = os.open("/tmp/com.llmserving.gateway.plist", os.O_WRONLY | os.O_CREAT | os.O_TRUNC, 0o600)
with os.fdopen(fd, "wb") as f:
    plistlib.dump(pl, f)
print("env keys:", ", ".join(sorted(env)))
PY
plutil -lint /tmp/com.llmserving.gateway.plist
```

```sh

sudo install -o root -g wheel -m 0644 /tmp/com.llmserving.gateway.plist /Library/LaunchDaemons/com.llmserving.gateway.plist
```

## 5. Point `tailscale serve` at the socket **(sudo: 건영)**
**What this Mac runs** (checked read-only on 2026-10-27): the standalone **macsys GUI app** 1.104.2, not the
open-source `tailscaled`.
- `/usr/local/bin/tailscale` is a 2-line shim that runs `/Applications/Tailscale.app/Contents/MacOS/Tailscale`.
- The daemon is the system extension `io.tailscale.ipn.macsys.network-extension`, running as root.
- The GUI app runs as 건영's login, and the agent runs as that same macOS account.
- `tailscale debug prefs` shows **no `OperatorUser` set**.

**How `--operator` behaves here:**
- `--operator` is the `tailscaled` (Linux and similar) mechanism for letting a non-root user change prefs and serve.
  On the macsys app, the logged-in GUI user gets LocalAPI access through the app regardless of operator.
- So `sudo tailscale set --operator=` is a harmless no-op on this Mac. Run it anyway, so the state is explicit and
  stays correct if the Mac ever moves to `tailscaled`.
- **Residual risk:** the agent's account is the console user, so it can still run `tailscale serve` without sudo.
  It could point serve back at TCP or at a socket it controls. The gateway would then stop honouring identity (TCP)
  or would not be involved at all.
- Mitigations: the agent's rules forbid serve changes (they need 건영), and §9 includes a `serve status` check.
  The real fix is running the agent under a separate macOS account; that is out of scope here.

```sh
sudo tailscale set --operator=                       # clear operator (no-op on macsys, explicit for tailscaled)
sudo tailscale serve --https=443 off
sudo tailscale serve --bg --https=443 unix:/opt/eve-gw/run/gw.sock
sudo tailscale serve status    # https://<TS_HOST> (tailnet only) |-- / proxy unix:/opt/eve-gw/run/gw.sock
scripts/check-serve.sh         # (no sudo) must print OK
sudo tailscale funnel status   # must show no funnel
```
If `sudo tailscale ...` errors (for example, the GUI shim refuses to run as root), run the same serve lines without
sudo from 건영's own Terminal. Do not let the agent run them.

Smoke test:
- From the iPhone or a tailnet browser, open `https://<TS_HOST>/ui`. It should log in as the allowlisted user, send a chat and save it.
- On the Mac, this must return **401**:
  ```sh
  curl -s -o /dev/null -w '%{http_code}\n' -H 'Tailscale-User-Login: <allowlisted login>' 127.0.0.1:8000/whoami
  ```
- With the API key on TCP, `/whoami` must report `"user":"api-key"`.
- The served UI must be 1.3.2 (not the 1.1.3 that used to be in `/opt/eve-gw/web`):
  ```sh
  curl -s https://<TS_HOST>/ui/sw.js | grep -q "CACHE = 'llmchat-1.3.2'" && echo 'UI OK'
  ```
- `sudo tail /opt/eve-gw/log/gateway.log` shows `"conn":"unix"` for UI requests and `"conn":"tcp"` for the curl.

### Optional pf rule **(sudo: 건영)**
This is defense in depth. Only `_evegw` and 건영 may open TCP connections to 127.0.0.1:8000.
- macOS pf `user` matching applies to sockets owned by local processes.
- Test it first with `sudo pfctl -vnf`.
- macOS updates can reset `/etc/pf.conf`; re-check after updates.
```sh
printf 'pass  out quick on lo0 proto tcp from any to 127.0.0.1 port 8000 user { _evegw, <ME> }\nblock return out quick on lo0 proto tcp from any to 127.0.0.1 port 8000\n' | sudo tee /etc/pf.anchors/eve-gw
sudo cp -p /etc/pf.conf /etc/pf.conf.pre-eve
echo 'anchor "eve-gw"
load anchor "eve-gw" from "/etc/pf.anchors/eve-gw"' | sudo tee -a /etc/pf.conf
sudo pfctl -vnf /etc/pf.conf && sudo pfctl -f /etc/pf.conf && sudo pfctl -E
```
Remove it with `sudo cp -p /etc/pf.conf.pre-eve /etc/pf.conf && sudo pfctl -f /etc/pf.conf`.

## 6. Phase 2 (later): close TCP :8000 **(sudo: 건영)**
Do this when `sudo grep '"conn":"tcp"' /opt/eve-gw/log/gateway.log` has been empty for 7 days.

**Limitation:** that grep sees only *authenticated* requests. The `request` log line is written after auth succeeds.
TCP requests rejected with 401/403 (a script without a key, or a client still sending identity headers) are **not**
counted. To find those too:
- watch the `auth` metric with provider `none` and result `denied` on `/metrics` for growth;
- sample clients with `lsof -nP -iTCP@127.0.0.1:8000 -sTCP:ESTABLISHED` a few times over the period.
1. Add `<key>GW_TCP_DISABLED</key><string>true</string>` to the daemon plist.
2. Restart: `sudo launchctl bootout system/com.llmserving.gateway` then `sudo launchctl bootstrap system /Library/LaunchDaemons/com.llmserving.gateway.plist`.
3. Health checks then need `sudo curl --unix-socket /opt/eve-gw/run/gw.sock http://x/health`.

## 10. Compensating controls for the accepted Med2 risk
The agent's account can still run `tailscale serve`; security accepted this as residual risk with two controls.

### 10a. Remove the funnel nodeAttr in the Tailscale admin console **(건영, browser; no sudo)**
State checked read-only on 2026-10-27: the node's `CapMap` has **no `funnel` capability**, serve has no
`AllowFunnel`, and `tailscale funnel status` says "tailnet only". So the policy already doesn't grant funnel to
this node. Keep it that way, and remove the attribute if it is ever added:
1. Go to admin console → **Access controls** (tailnet policy file).
2. In `"nodeAttrs"`, find entries whose `"attr"` contains `"funnel"` and whose `"target"` matches this node, its tag,
   its owner, `autogroup:member` or `*`. Remove `"funnel"` from that `attr` list, or narrow the target so it
   excludes this node. Save.
3. Verify on the Mac (read-only):
   ```sh
   tailscale status --json | python3 -c 'import json,sys;s=json.load(sys.stdin)["Self"];print([c for c in list(s.get("CapMap") or {})+(s.get("Capabilities") or []) if "funnel" in c] or "no funnel cap")'
   scripts/check-serve.sh      # also fails if a funnel capability appears
   ```
   With the attribute gone, `tailscale funnel 443 on` fails with a "Funnel not available" error. Don't run that
   on prod as a test.

### 10b. Scheduled serve check *(no sudo, read-only)*
`scripts/check-serve.sh` exits 0 only if all of the following hold:
- serve has exactly one handler, `/` → `$EXPECT` on HTTPS 443, with no other TCP, Services or Foreground config;
- funnel is off;
- the node has no funnel capability.

It exits 1 on any drift and 2 if it can't read the state.
```sh
EXPECT=http://127.0.0.1:8000 scripts/check-serve.sh   # before cutover
scripts/check-serve.sh                                # after §5 (default EXPECT=unix:/opt/eve-gw/run/gw.sock)
```
Schedule it (cron/launchd, owner's choice). Treat a non-zero exit as an incident: someone changed serve.
