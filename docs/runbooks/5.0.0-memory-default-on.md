# Runbook: 5.0.0 memory default-on (MAJOR)

Contract: PR #54 (memory.md §14, ui-api-contract §3.9.7). Do not deploy until #53 is merged, every §14.1
precondition holds and 보안 담당 has given final approval.

## What changes
- Server `memory.enabled` / `GW_MEMORY_ENABLED` defaults to **true**. Default `audit_key_file` is
  `~/llm-serving/etc/memory_audit.key`; startup still refuses if it is missing or invalid (fail-closed).
- Per-user `memory.enabled`: missing key reads **true** (opt-out); an explicit `false` stays off.
- New setting `ui.memory_intro_seen` (bool, default false, PATCH from a browser session only).
  Until it is true, nothing is injected into prompts and the `memory.propose` tool is not offered.
  Viewing, editing, deleting and exporting stay available.
- The api-key virtual user (Bearer) has memory fixed off: no injection, no tool, and every `/v1/memory*`
  route answers 403 `scope_denied`. `PATCH /v1/settings` with Bearer is 403 `scope_denied` (unchanged).
- Off paths are unchanged: user off → POST items / propose / approve = 403 `kill_switch`.

## Settings schema
| Key | Type, default | PATCH validation |
|---|---|---|
| `memory.enabled` | bool, true (5.0.0) | bool only; 400 `invalid` if `system.memory_available=false` |
| `ui.memory_intro_seen` | bool, false | bool only; null, other types or unknown `ui.*` keys → 400 `invalid`; allowed even when memory is unavailable |

`GET /v1/settings` always includes `"ui":{"memory_intro_seen":…}`.

## Before deploy
Follow memory.md §14.2 (audit key, data_dir 0700/0600, tmutil exclusion, not in a sync folder).

## Rollback (about 1 minute, no data change)
1. In `config.yaml` set `memory.enabled: false` (or `GW_MEMORY_ENABLED=false` in the plist; env wins).
2. Restart the gateway.
3. Check: `GET /v1/settings` → `system.memory_available=false`; `/v1/memory` → 404.
4. Memory files stay on disk untouched. Deleting them needs 건영's explicit approval.
