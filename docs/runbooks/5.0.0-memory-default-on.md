# Runbook: 5.0.0 memory default-on (MAJOR)

Contract: PR #54 (memory.md §14, ui-api-contract §3.9.7). Do not deploy until #53 is merged, every §14.1
precondition holds and 보안 담당 has given final approval.

## What changes
- Server `memory.enabled` / `GW_MEMORY_ENABLED` defaults to **true**. Default `audit_key_file` is
  `~/llm-serving/etc/memory_audit.key`; startup still refuses if it is missing or invalid (fail-closed).
- Per-user `memory.enabled`: missing key reads **true** (opt-out); an explicit `false` stays off.
- New setting `ui.memory_intro_seen` (bool, default false, PATCH from a browser session only).
  Until it is true, nothing is injected into prompts and the `memory.propose` tool is not offered.
  Viewing, editing, deleting and exporting stay available.
- The api-key virtual user (Bearer) has memory fixed off: no injection, no tool, and every `/v1/memory*`
  route answers 403 `scope_denied`. `PATCH /v1/settings` with Bearer is 403 `scope_denied` (unchanged).
- Off paths are unchanged: user off → POST items / propose / approve = 403 `kill_switch`.

## Settings schema
| Key | Type, default | PATCH validation |
|---|---|---|
| `memory.enabled` | bool, true (5.0.0) | bool only; 400 `invalid` if `system.memory_available=false` |
| `ui.memory_intro_seen` | bool, false | bool only; null, other types or unknown `ui.*` keys → 400 `invalid`; allowed even when memory is unavailable |

`GET /v1/settings` always includes `"ui":{"memory_intro_seen":…}`.

The intro hold applies only to prompt injection and model proposals. A direct, user-initiated memory add works even before the intro is seen.

## Before deploy
Follow memory.md §14.2 (audit key, data_dir 0700/0600, tmutil exclusion, not in a sync folder).

## Rollback (about 1 minute, no data change)
Since 4.0.0 the gateway is the LaunchDaemon `system/com.llmserving.gateway` (plist
`/Library/LaunchDaemons/com.llmserving.gateway.plist`, `UserName` `_evegw`), and its config is
`/opt/eve-gw/etc/config.yaml`. Not the old per-user LaunchAgent. Each block below runs in its own
`bash -euo pipefail` heredoc (paste it as is; `SH` must stay at column 0), so a failed check stops
that block without closing your interactive shell. A block checks that its target exists and
**stops right there** if not, so an empty `grep` can never pass silently as "unset".

### Step 1. Turn memory off
Set `memory.enabled: false` in `/opt/eve-gw/etc/config.yaml` (recommended; exactly `true` or `false`).
Resolution is "off wins": either `memory.enabled: false` or `GW_MEMORY_ENABLED=false` alone turns memory
off. Then check (no `GW_MEMORY_ENABLED` output = unset, valid only because the existence checks passed):

```sh
bash -euo pipefail <<'SH'
P=/Library/LaunchDaemons/com.llmserving.gateway.plist
J=system/com.llmserving.gateway
C=/opt/eve-gw/etc/config.yaml
sudo test -f "$P" || { echo "missing $P, stop"; exit 1; }
sudo launchctl print "$J" >/dev/null 2>&1 || { echo "job $J not loaded, stop"; exit 1; }
sudo test -f "$C" || { echo "missing $C, stop"; exit 1; }
# memory.enabled only (not web.enabled etc.): scoped to the top-level memory: block
v=$(sudo awk '/^[^[:space:]#]/{m=($1=="memory:")} m && /^[[:space:]]+enabled:/{sub(/#.*/,"");print $2}' "$C")
echo "config memory.enabled=${v:-<unset>}"
sudo plutil -p "$P" | grep GW_MEMORY_ENABLED || echo "plist GW_MEMORY_ENABLED unset"
sudo launchctl print "$J" | grep GW_MEMORY_ENABLED || echo "job GW_MEMORY_ENABLED unset"
SH
```

The `awk` only reads block style. Flow style such as `memory: {enabled: false}` shows `<unset>` here;
in that case judge by the startup log in step 2, which is authoritative anyway.

A leftover `GW_MEMORY_ENABLED=true` does not block the rollback, but remove it so the intent is clear.
Never leave it set but empty: an empty/whitespace or non-`true`/`false` `GW_MEMORY_ENABLED`, or a
`memory.enabled` that is null/empty or not exactly `true`/`false` (e.g. `on`, `yes`, `TRUE`, `"false"`,
`!!str false`), is a startup error (fail closed). Unknown keys in the config (e.g. a typo `enable:`) are
also a startup error.

### Step 2. Restart and judge by the startup log

```sh
bash -euo pipefail <<'SH'
J=system/com.llmserving.gateway
sudo launchctl print "$J" >/dev/null 2>&1 || { echo "job $J not loaded, stop"; exit 1; }
sudo launchctl kickstart -k "$J"   # runs as _evegw
SH
```

The one startup log line must read `msg="memory config resolved" memory_enabled=false
memory_enabled_source=<config|env|default>` (if both are set and one is false, the source is the one
that said false; both false -> `env`). Anything other than `memory_enabled=false` means the rollback
did not take effect.

### Step 3. Check the API
`GET /v1/settings` → `system.memory_available=false`; `/v1/memory` → 404.

### Step 4. Data
Memory files stay on disk untouched. Deleting them needs 건영's explicit approval.
